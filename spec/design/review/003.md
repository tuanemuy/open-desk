# レビュー #003: /critique — UX・デザイン品質・一貫性

Phase: Step 1 (Visual) + Step 2 (/critique)

## AIスロップ判定: 合格

このデザインはAI生成っぽく見えない。以下の点でクリア:
- ダークモード + グローイングアクセントのテンプレ回避
- グラデーションテキスト不使用
- グラスモーフィズム不使用
- ヒーローメトリクスレイアウト不使用
- 同一カードグリッドの繰り返し回避（各ウィジェットが異なるコンテンツ構造）
- 色使いが控えめで意図的

**注意点**: Inter フォント使用は frontend-design ガイドラインの DON'T に該当するが、業務アプリプラットフォームとして実用性を優先した意図的な選択と判断。問題なし。

## 全体的な印象

Clean Neutral の方向性は良く実現されている。控えめなブルーアクセント、余白の活用、ボーダーベースの区切りなど、デザイン方針に忠実。ただし、**前回レビュー（#001）で修正済みとされたヘッダー統一が不完全**であり、実際には2つの異なるHTML/CSS実装が残存している。

## うまくいっていること

1. **カラーシステムの一貫性**: OKLCHベースのトークンが全ファイルの `:root` で統一されており、`color: white` のハードコードも `var(--color-on-primary)` に正しく置換済み
2. **ビジュアル階層**: 各画面でプライマリアクション（保存ボタン、投稿ボタン等）が視覚的に明確。見出し→本文→補足の階層がフォントサイズ・ウェイトで適切に表現されている
3. **情報アーキテクチャ**: ポータルの2カラム構成、アプリのテーブル+ツールバー、設定のサイドバー+コンテンツなど、ページタイプに応じた適切なレイアウトパターンが使い分けられている

## 対応が必要な問題

### P1: ヘッダーのHTML/CSS構造が依然2パターン存在（高）

**何が**: 前回レビュー #001 の P1 で「修正済み」とされたが、実際には2つの異なる実装が残存している。

| 項目 | Group A (space, people, space-thread, message) | Group B (portal, notifications, app-list, record-detail, record-form, search, app-settings, personal-settings) |
|------|-----------------------------------------------|--------------------------------------------------------------------------------------------------------------|
| container class | `.global-header-inner` | `.header-inner` |
| nav markup | `<ul class="global-nav"><li><a>` | `<nav class="header-nav"><a>` |
| search input | `class` なし、placeholder 独自 | `class="search-input"` |
| search SVG | viewBox `0 0 16 16` | viewBox `0 0 24 24` + stroke-linecap/linejoin |
| avatar class | `.user-avatar-header`（3ファイル）/ `.user-avatar`（1ファイル） | `.user-avatar` |

**なぜ重要か**: ヘッダーはプロダクト全体のアイデンティティ。構造が異なると実装時にコンポーネント化できず、保守コストが上がる。また、CSSの適用が異なるため、微妙なレンダリング差異が生じるリスクがある。

**修正**: Group B（portal.html基準）のパターンに全ファイルを統一する。具体的には space.html, people.html, space-thread.html, message.html の4ファイルのヘッダーを書き換え。

### P2: 検索プレースホルダーの不統一（中）

**何が**: コンテキストに応じたプレースホルダーが定義されているが、ルールが不明確。

| プレースホルダー | 使用ファイル |
|----------------|------------|
| `検索...` | portal, notifications, personal-settings, search |
| `アプリ内検索` | app-list, record-detail, record-form, app-settings |
| `全体検索` | people, message |
| `スペース内検索` | space, space-thread |

**なぜ重要か**: 「検索...」と「全体検索」が混在。ポータルやnotificationsは全体コンテキストなので「全体検索」が適切。

**修正**: ルールを明確化して統一する:
- アプリ画面内 → `アプリ内検索`
- スペース画面内 → `スペース内検索`
- それ以外（グローバルコンテキスト） → `全体検索`

対象: portal.html, notifications.html, personal-settings.html, search.html の placeholder を `全体検索` に変更。

### P3: ハードコードされた font-size（低）

**何が**: トークン範囲外のフォントサイズがハードコードされている。

| 値 | ファイル | 用途 |
|----|---------|------|
| `10px` | app-settings.html, space-thread.html | 必須マーク、サイドバータイムスタンプ |
| `11px` | message.html, space-thread.html | 通知バッジ |

**なぜ重要か**: トークンシステムの一貫性。`--text-xs` の最小値（11px）より小さい値が使われている。

**修正**: すべて `var(--text-xs)` に統一。微小テキストが必要な場合でも 11px（--text-xs の下限）を下回らない。

### P4: border-radius: 2px（低）

**何が**: search.html の `.highlight` クラスで `border-radius: 2px` がハードコード。トークンの最小値は `--radius-sm: 4px`。

**修正**: `var(--radius-sm)` を使用。

## 軽微な観察事項

- **コンポーネントサイズのハードコード**: `height: 56px`（ヘッダー）、`width: 240px`（サイドバー）等は全ファイルで統一されているため、実装時にコンポーネントトークンとして抽出する候補。デザインフェーズでは許容。
- **6px padding**: 前回レビューの P4 と同じ。実装フェーズで対応。

## 修正対象

- [x] P1: Group A（4ファイル: space, people, space-thread, message）のヘッダーを Group B パターンに統一
- [x] P2: 検索プレースホルダーのルール統一（portal, notifications, personal-settings, search → 「全体検索」に変更）
- [x] P3: ハードコード font-size を `var(--text-xs)` に修正（space-thread: 10px/11px, message: 11px×2, app-settings: 10px）
- [x] P4: `border-radius: 2px` → `var(--radius-sm)`（search.html）
