# ADR-001: ドメイン境界の定義

## ステータス

承認済み

## コンテキスト

OpenDeskはノーコードの業務アプリ構築プラットフォームであり、アプリ管理、レコード操作、チームコラボレーション、通知、検索、管理機能など多岐にわたる機能を持つ。これらの機能を適切なドメイン境界で区切り、DDDに基づく設計を行う必要がある。

## 決定

12のドメインに分割する。種別はCore / Supporting / Genericの3段階とする。

**Core（2ドメイン）**: App、Record
- システムの中核的な価値を提供し、最も複雑なビジネスロジックを持つ
- Appは「スキーマ/設定」側、Recordは「データ/操作」側と明確に分離

**Supporting（4ドメイン）**: Identity、AccessControl、Space、Notification
- Coreドメインを支える重要な機能だが、相対的にビジネスロジックの複雑さは低い

**Generic（6ドメイン）**: Portal、People、Message、File、Search、Bookmark
- 汎用的な機能であり、ビジネス上の差別化要因が少ない

## 検討した代替案

### 案1: AppとRecordを1つのドメインにする
- 不採用理由: Appは「アプリの構造定義」（フォーム設計、ビュー、グラフ等）、Recordは「データ操作」（CRUD、コメント、履歴等）と関心事が明確に異なる。1つにまとめると集約が肥大化し、変更の影響範囲が広がる。

### 案2: AccessControlをIdentityに含める
- 不採用理由: AccessControlはアプリ・レコード・フィールドの3レベルでACLを管理し、条件ベースのルール評価を行う。Identity（ユーザー・組織・グループの管理）とは責務が異なり、AppやRecordからも参照される独立した関心事。

### 案3: プロセス管理を独立ドメインにする
- 不採用理由: プロセス管理の「設定」面（ステータス定義、遷移ルール）はApp内のアプリ設定として自然に収まり、「実行」面（ステータス変更、ワーカー割当）はRecordの操作として自然に収まる。独立ドメインにすると両方への依存が生まれ、オーバーヘッドが増える。

### 案4: PeopleをIdentityに含める
- 不採用理由: Identityは認証・組織構造という「システム管理」の関心事を扱い、Peopleはプロフィール表示・ステータス投稿・フォローという「ソーシャル」の関心事を扱う。ユビキタス言語が異なるため分離した。

### 案5: PortalやBookmarkなどの薄いドメインを他に統合する
- 不採用理由: 各ドメインは独自のユビキタス言語を持ち、境界が明確。薄いドメインでも将来的な機能拡張に対応しやすく、コードの変更影響範囲が限定される。

## 影響

- 12ドメインと多いが、Generic 6ドメインはエンティティ数が少なく設計・実装コストは低い
- ドメイン間の参照はすべてIDで行い、直接参照は禁止する
- ドメイン間の連携はユースケース層でオーケストレーションする
- 依存は一方向のみ（循環なし）で、変更の影響波及を抑制できる
