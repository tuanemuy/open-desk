## 1. 認証方式

OpenDesk REST API では、以下の4つの認証方式が利用できる。
複数の認証方式が指定された場合の優先順位は以下のとおり。

| 優先順位 | 認証方式 |
|---------|---------|
| 1 | パスワード認証 |
| 2 | APIトークン認証 |
| 3 | OAuthクライアント認証 |
| 4 | セッション認証 |

### 1.1 パスワード認証

ユーザーのログイン名とパスワードを使った認証方式。

| 項目 | 内容 |
|------|------|
| ヘッダー名 | `X-Cybozu-Authorization` |
| エンコード方式 | `ログイン名:パスワード` を Base64 エンコード |
| 制限事項 | 2要素認証を有効にしたユーザーは利用不可 |

**リクエスト例:**

ログイン名が `Administrator`、パスワードが `cybozu` の場合:

```
X-Cybozu-Authorization: QWRtaW5pc3RyYXRvcjpjeWJvenU=
```

**セキュリティ環境での注意:**

- **IPアドレス制限が有効な環境:** Basic認証ヘッダーを追加で付与する必要がある。
  ```
  Authorization: Basic [Base64エンコード値]
  ```
- **SAML認証環境:** cybozu.com のログイン名とパスワードを指定する。SAML認証のみに制限されている場合、パスワード認証はシステム管理者のみ利用可能。
- **クライアント証明書が必要な環境:** URLに `.s` を挿入する（例: `sample.s.cybozu.com`）。

### 1.2 APIトークン認証

アプリごとに生成されるAPIトークンを使った認証方式。

| 項目 | 内容 |
|------|------|
| ヘッダー名 | `X-Cybozu-API-Token` |
| トークン取得 | アプリの設定画面から生成 |
| トークン上限 | 1アプリにつき最大20個 |
| 操作記録 | APIトークンによる操作は Administrator として記録される |
| 制限事項 | カスタマイズ形式の一覧を含まないアプリのみ対応 |

**リクエスト例:**

```
X-Cybozu-API-Token: BuBNIwbRRaUvr33nWXcfUZ5VhaFsJxN0xH4NPN92
```

**複数トークンの指定:**

1回のリクエストで複数のAPIトークンを指定できる（最大9個まで。10個以上はエラー）。
カンマ区切り、または複数のヘッダーで指定可能。

```
X-Cybozu-API-Token: token1, token2, token3
```

### 1.3 セッション認証

Webブラウザーで cybozu.com にログイン済みの場合に、そのセッションを使って認証する方式。

| 項目 | 内容 |
|------|------|
| 利用場面 | ブラウザーでcybozu.comにログイン済みのとき |
| 必須ヘッダー | `X-Requested-With: XMLHttpRequest`（または空以外の文字列） |
| CSRF対策 | POST/PUT/DELETE メソッド使用時はCSRFトークンの付与が必要 |

**利用方法:**

- **OpenDesk カスタマイズJS内:** `openDesk.api()` メソッドを使用（セッション認証を自動処理）
- **ブラウザーから直接:** Fetch API または XMLHttpRequest を使用し、`X-Requested-With` ヘッダーを付与

**Garoon連携の場合:** リクエストヘッダーに `X-Requested-With` を付与し、OpenDesk連携用トークンを使用する。

### 1.4 OAuth認証（OAuth 2.0）

外部サービスからOpenDesk APIを利用する場合に、ユーザーのID/パスワードを保存せずに認証できる方式。

| 項目 | 内容 |
|------|------|
| フロー | Authorization Code Grant（認可コードグラント） |
| クライアントタイプ | Confidential Client |
| アクセストークン有効期間 | 1時間 |
| リフレッシュトークン有効期間 | 無期限 |
| リフレッシュトークン上限 | 1クライアントあたり1ユーザーにつき最大10個 |
| 認可コード有効期間 | 10分 |

**OAuthフローの流れ:**

1. cybozu.com の管理画面で OAuthクライアントを登録（クライアントID、クライアントシークレットが自動生成される）
2. リダイレクトURLとスコープを設定
3. 認可エンドポイントにユーザーをリダイレクトし、認可コードを取得
4. トークンエンドポイントに POST リクエストを送信し、アクセストークンを取得
5. アクセストークンの有効期限切れ時はリフレッシュトークンで新しいアクセストークンを取得

**トークンエンドポイント例:**

```
POST https://sample.cybozu.com/oauth2/token
```

Authorization ヘッダーに `クライアントID:クライアントシークレット` を Base64 エンコードした値を指定する。

```
Authorization: Basic [Base64エンコード値]
```

リクエストボディに `grant_type`、`redirect_uri`、`code` を含める。

**OpenDesk 用 OAuth スコープ一覧:**

| スコープ | 説明 |
|---------|------|
| `k:app_record:read` | レコードの取得（1件/複数件の取得、コメント取得など） |
| `k:app_record:write` | レコードの登録・更新・削除、ステータス変更、コメント投稿・削除など |
| `k:app_settings:read` | アプリ情報取得、フォーム設計情報、フィールド取得、一覧設定、グラフ設定、アクセス権設定など（17種類の読み取り操作） |
| `k:app_settings:write` | フィールド追加・変更・削除、レイアウト変更、通知設定、アクセス権管理、運用環境への反映など（17種類の書き込み操作） |
| `k:file:read` | ファイルダウンロード |
| `k:file:write` | ファイルアップロード |

スコープを複数指定する場合はスペースで区切る。

### 1.5 ゲストユーザーの制限

ゲストユーザーは **セッション認証のみ** 利用可能。パスワード認証、APIトークン認証、OAuth認証は使用できない。

## 2. 共通リクエスト仕様

### 2.1 ベースURL構造

**通常のスペース:**

```
https://{サブドメイン}.cybozu.com/k/v1/{リソース}
```

**ゲストスペース:**

```
https://{サブドメイン}.cybozu.com/k/guest/{スペースID}/v1/{リソース}
```

**プレビュー環境（動作テスト環境）:**

```
https://{サブドメイン}.cybozu.com/k/v1/preview/{リソース}
```

**ゲストスペースのプレビュー環境:**

```
https://{サブドメイン}.cybozu.com/k/guest/{スペースID}/v1/preview/{リソース}
```

### 2.2 Content-Type

| 場面 | Content-Type |
|------|-------------|
| JSON形式のリクエストボディ | `application/json` |
| ファイルアップロード | `multipart/form-data` |
| リクエストボディなし | 指定不要 |

### 2.3 リクエストヘッダー

| ヘッダー名 | 用途 | 説明 |
|-----------|------|------|
| `Host` | 必須 | ドメイン:ポート番号（443）形式 |
| `X-Cybozu-Authorization` | パスワード認証 | `ログイン名:パスワード` を Base64 エンコード |
| `X-Cybozu-API-Token` | APIトークン認証 | OpenDesk で生成したAPIトークン |
| `X-Requested-With` | セッション認証 | `XMLHttpRequest` または空以外の文字列 |
| `Authorization` | Basic認証 / OAuth | Basic認証値 または Bearer トークン |
| `X-HTTP-Method-Override` | メソッドオーバーライド | `GET` / `POST` / `PUT` / `DELETE`（大文字）。リクエストURLが長い場合（8KB超）に POST メソッドで GET 相当のリクエストを送信するために使用 |
| `Accept-Language` | 表示言語指定 | cybozu.com の表示言語コード |

### 2.4 文字コード

| 対象 | 文字コード |
|------|-----------|
| リクエストボディ | UTF-8 |
| レスポンスボディ | UTF-8 |

### 2.5 日時フォーマット

| 操作 | フォーマット | 備考 |
|------|------------|------|
| 取得時 | `YYYY-MM-DDTHH:MM:SSZ` | UTC |
| 登録/更新時 | `YYYY-MM-DDTHH:MM:SS±HH:MM` または `YYYY-MM-DDTHH:MM:SSZ` | タイムゾーンオフセット指定可 |

秒情報は登録/更新時に指定しても無視される。

### 2.6 その他の仕様

- **JSON文字列:** バックスラッシュによるエスケープが必要
- **クエリパラメータ:** URLパーセントエンコーディングに対応
- **配列型パラメータ:** 要素ごとに分解してからエンコーディング
- **監査ログ:** REST API の実行は自動的に監査ログに記録される

## 3. 共通レスポンス仕様

### 3.1 レスポンス形式

| 形式 | 対象 |
|------|------|
| JSON（UTF-8） | 通常のAPIレスポンス |
| バイナリデータ | ファイルダウンロードAPI |

### 3.2 HTTPステータスコード

| 区分 | ステータスコード | 説明 |
|------|----------------|------|
| 成功 | 200番台 | リクエストが正常に処理された |
| クライアントエラー | 400 | 不正なリクエスト（バリデーションエラー等） |
| 認証エラー | 401 | 認証情報が不正または不足 |
| 権限エラー | 403 | アクセス権限がない |
| 未検出 | 404 | リソースが見つからない |
| レート制限超過 | 429 | 同時接続数の上限を超過 |
| サーバーエラー | 500番台 | サーバー側のエラー |

## 4. エラーレスポンス

### 4.1 エラーレスポンスのJSON構造

リクエストが失敗した場合、200番台以外のHTTPステータスコードとともに以下のJSON構造でエラーが返される。

```json
{
  "id": "1505999166-897850006",
  "code": "CB_IJ01",
  "message": "不正なJSON文字列です。"
}
```

| プロパティ | 型 | 説明 |
|-----------|-----|------|
| `id` | 文字列 | エラーID。サイボウズサポートへの問い合わせ時に使用 |
| `code` | 文字列 | エラーコード。エラーの種類を識別 |
| `message` | 文字列 | エラーメッセージ。エラーの内容を説明 |

### 4.2 主要なエラーコード

| エラーコード | 説明 |
|-------------|------|
| `CB_IJ01` | 不正なJSON文字列 |
| `CB_AU01` | 認証に失敗（ログイン名またはパスワードが不正） |
| `CB_NO02` | アクセス権限がない |
| `CB_VA01` | バリデーションエラー（入力値が不正） |
| `CB_IL02` | 不正なフィールド値 |
| `GAIA_RE18` | レコードの取得件数がlimitの上限を超過 |
| `GAIA_DA02` | レコードが存在しない |

※ エラーコードの完全な一覧は個別APIドキュメントを参照のこと。

## 5. 制限事項

### 5.1 同時接続数

| 項目 | 制限値 |
|------|--------|
| 1ドメインあたりの同時接続数 | **100** |
| 超過時のHTTPステータス | **429** |

- 長時間にわたって100を超える状態が続くと、REST APIを使用していないアプリでもレスポンス遅延や429エラーが発生することがある。
- 同時接続数の増加を完全に防ぐ方法はないため、不要なAPIリクエストの削減や監視・分岐処理の組み込みが推奨される。

### 5.2 APIリクエスト数（1日あたり）

| コース | 制限値 |
|--------|--------|
| スタンダードコース | 1アプリあたり **10,000件/日** |
| ワイドコース | 1アプリあたり **100,000件/日** |

- リセットタイミング: 毎日午前9:00（JST）
- 収集期間: 9:00 ~ 翌日8:59（JST）
- 超過時: 翌日9時頃に管理者メールアドレス宛に超過メールが送信される
- 他ユーザー環境に重大な影響を及ぼす場合、API処理が中断されることがある
- カウント方法: 1回のAPI呼び出しを1リクエストとしてカウント（例: GET で500件取得 = 1リクエスト）
- 一部のREST APIはカウント対象外

### 5.3 レコード操作の制限

| 操作 | 制限値 |
|------|--------|
| 一度に取得できるレコード数（GET） | **500件**（limitの初期値は100件） |
| offset の上限 | **10,000件** |
| 一度に登録/更新/削除できるレコード数 | **100件** |
| レコードコメント取得 | 1度に **10件** |
| フィールド指定数（リクエストボディ） | 最大 **1,000個** |
| フィールド指定数（クエリ文字列） | 添字 **0~99**（100個） |
| キーワード検索の打ち切り | 該当レコードが **100,000件** に達した時点 |

### 5.4 カーソルAPIの制限

| 項目 | 制限値 |
|------|--------|
| 1ドメインあたりの有効カーソル数 | 最大 **10個** |
| カーソルの有効期限 | 最終操作から **10分** |
| カーソル作成のタイムアウト | **5分** |
| 並行カーソル作成 | 不可（リクエストは待機される） |

カーソルAPIは offset を利用する方法と比べ、ソート条件やレコード件数によらずレコード取得時間が安定している。offset の10,000件制限を回避するためにも推奨される。

### 5.5 その他の制限

| 項目 | 制限値 |
|------|--------|
| アップロードファイルの保持期間 | 未使用の場合 **3日間** で自動削除 |
| 1アプリあたりのAPIトークン数 | 最大 **20個** |
| 1リクエストあたりのAPIトークン指定数 | 最大 **9個**（10個以上でエラー） |
| OAuthリフレッシュトークン数 | 1クライアント1ユーザーあたり最大 **10個** |

## 6. APIアップデートポリシー

参照元: https://cybozu.dev/ja/OpenDesk/docs/overview/update-policy/

### 6.1 基本方針

- APIの互換性に留意してアップデートを行う。
- ただし、製品改善やセキュリティリスク低減のために必要と判断した場合、既存APIの仕様変更や廃止を伴うアップデートを行う場合がある。

### 6.2 事前告知

| 状況 | 告知タイミング |
|------|--------------|
| 通常のアップデート | 定期メンテナンスの **4週間前** までに告知 |
| 対応コストが大きいアップデート | より **早期** に告知 |
| 緊急性の高い脆弱性/不具合修正 | 事前告知なしの場合がある |

### 6.3 アップデートスケジュール

- **定期メンテナンス:** 毎月第2日曜に実施
- APIアップデートは定期メンテナンス時に月例チャネルにリリースされる

### 6.4 アップデートオプション

リリース後の影響に対応するため、以下の仕組みが用意されている。

| オプション | 内容 |
|-----------|------|
| 先行利用機能 | 新機能を事前にテスト可能（利用期間は都度調整） |
| 無効化オプション | リリース後、原則として **3ヵ月以上** の無効化可能期間を設定 |

## 7. プレビュー環境とデプロイ

### 7.1 プレビュー環境（動作テスト環境）の概要

OpenDesk では、アプリの設定変更を直接運用環境に反映するのではなく、まず「プレビュー環境（動作テスト環境）」で変更を行い、確認後に運用環境へデプロイするフローを採用している。

**プレビュー用エンドポイント:**

通常のエンドポイントパスに `/preview/` を挿入する。

| 環境 | URLパターン |
|------|-----------|
| 運用環境 | `/k/v1/{リソース}.json` |
| プレビュー環境 | `/k/v1/preview/{リソース}.json` |
| ゲストスペース（運用） | `/k/guest/{スペースID}/v1/{リソース}.json` |
| ゲストスペース（プレビュー） | `/k/guest/{スペースID}/v1/preview/{リソース}.json` |

### 7.2 設定変更の反映フロー

REST API を使ったアプリの作成・設定変更は、以下の3ステップで行う。

#### STEP 1: プレビュー環境でのアプリ作成

- 動作テスト環境（プレビュー環境）にアプリを作成する。
- この段階ではアプリはまだ使用不可。
- 既存アプリの設定変更時はこのステップをスキップ。

#### STEP 2: アプリ設定の構成

プレビュー環境向けAPIを使って設定を変更する。主な設定変更API:

- 一覧設定の変更
- フィールドの追加・変更・削除
- フォームレイアウトの変更
- アプリの一般設定変更
- アクセス権設定（アプリ/レコード/フィールド別）
- プロセス管理設定
- JavaScript/CSSカスタマイズ設定
- 通知設定

#### STEP 3: 運用環境への反映（デプロイ）

「アプリの設定を運用環境へ反映する」APIを実行する。これは OpenDesk 画面の「アプリを更新」ボタンのクリックに相当する。

### 7.3 デプロイAPI

**アプリの設定を運用環境へ反映する:**

| 項目 | 内容 |
|------|------|
| HTTPメソッド | POST |
| エンドポイント | `/k/v1/preview/app/deploy.json` |
| ゲストスペース | `/k/guest/{スペースID}/v1/preview/app/deploy.json` |
| Content-Type | `application/json` |
| 認証方式 | パスワード認証、APIトークン認証、セッション認証、OAuth認証 |
| 必要な権限 | アプリ管理権限 |

**リクエストパラメータ:**

| パラメータ | 型 | 必須 | 説明 |
|-----------|-----|------|------|
| `apps` | 配列 | 必須 | アプリID一覧（最大300件） |
| `apps[].app` | 数値/文字列 | 必須 | アプリID |
| `revision` | 数値/文字列 | - | 期待するリビジョン番号。不一致時エラー（`-1` で検証スキップ） |
| `revert` | 真偽値 | - | `true`: 変更をキャンセル、`false`: 運用環境へ反映（デフォルト: `false`） |

**レスポンス:** なし（空レスポンス）

**特記事項:**

- 非同期処理で動作する。反映状況の確認には別途APIを使用。
- 最大300アプリを同時に処理可能。
- 1つでも失敗すると、すべてのアプリが実行前の状態に戻る（トランザクション）。
- 実行完了前に他の設定変更APIを実行するとエラーになる（排他制御）。
- アクセス権の変更結果は完了したものから順次反映される。

### 7.4 デプロイ状況確認API

**アプリの設定の運用環境への反映状況を確認する:**

| 項目 | 内容 |
|------|------|
| HTTPメソッド | GET |
| エンドポイント | `/k/v1/preview/app/deploy.json` |
| ゲストスペース | `/k/guest/{スペースID}/v1/preview/app/deploy.json` |
| 認証方式 | パスワード認証、APIトークン認証、セッション認証、OAuth認証 |
| 必要な権限 | アプリ管理権限 |

**リクエストパラメータ:**

| パラメータ | 型 | 必須 | 説明 |
|-----------|-----|------|------|
| `apps` | 配列（数値/文字列） | 必須 | アプリID一覧（最大300件） |

**レスポンス:**

| プロパティ | 型 | 説明 |
|-----------|-----|------|
| `apps` | 配列 | 処理状況オブジェクトの配列 |
| `apps[].app` | 文字列 | アプリID |
| `apps[].status` | 文字列 | 処理ステータス |

**ステータス値:**

| ステータス | 説明 |
|-----------|------|
| `PROCESSING` | 処理中 |
| `SUCCESS` | 処理完了 |
| `FAIL` | 処理失敗 |
| `CANCEL` | 他のアプリの失敗により処理がキャンセルされた |
